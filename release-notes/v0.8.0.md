A breaking release: `flatten` writes a pointwise-lifted state differently. The `.esm` format stays at **esm 1.3.0**, and every document that loaded under 0.7.0 loads unchanged.

## Breaking changes

- **A pointwise-lifted state names its index sets** (esm-libraries-spec §4.7.5, "Pointwise lift: index sets"). When `flatten` lifts a scalar state onto an operator's grid (esm-spec §10.5), every binding now records the same three things:
  - **The lifted state's `shape`** in `state_variables` is the grid's index sets, such as `["lon", "lat"]`. Python, Rust, TypeScript and Go used to leave the shape empty. Julia already wrote one.
  - **Both lifted `faq` nodes range each loop over its index set**, `{"from": "lon"}`, printed `i in lon`. Python, Rust, TypeScript and Go used to write the interval `[1, 4]`.
  - **`lifted_shapes` is unchanged**: it still holds the extents, now the sizes of the index sets in the state's `shape`.

  Each dimension's index set is the one an operand gathered at the lift's loops is declared on, else the only declared index set of the dimension's size. When neither decides, the dimension gets a synthetic interval `_liftdim<d>_<extent>`, which the flattened `index_sets` gains. Julia used to give such a dimension that name in the shape without adding it to `index_sets`, and ranged it as an interval. A document that declares an index set of that name with a different size is now refused with the binding's dimension-promotion error. Code that read a lifted `faq`'s ranges as intervals, or that recovered a lifted state's index sets by matching extents against other variables' shapes, should read the state's `shape` instead. The `pointwise_lift` tier of `tests/conformance/flatten/cases.json` pins the result in all five bindings.

## Other changes

- **Julia: an operator's `ic(_var)` gives every state its own initial condition.** An `operator_compose` operator that writes `ic(_var) ~ e` is now expanded once per state, as `D(_var)` already was, so `field_ics` holds one entry per state (esm-libraries-spec §4.7.1 step 3). Julia used to record one entry under `_var`, so a consumer that writes initial conditions from `field_ics` built a different initial state from Julia than from the other bindings, which already expanded it.

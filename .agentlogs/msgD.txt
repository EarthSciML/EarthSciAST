fix(tests): repair corpus defect 1, and diagnose defect 3 as a resolver bug

Corpus defect 1 -- FIXED. The recorded diagnosis was wrong. It said the
index-set-producing node "was described and never written", and that repairing
it was fixture work needing the RFC author's intent. Both facts it rested on
were true -- from_faq named "edge_set", a recursive walk found zero "id" keys,
and "edge_set" appeared only in the from_faq and in an _comment -- but the
inference was not. The _comment is the doc-comment ON that node, a sibling of
the lhs/rhs it annotates, and its first words say so.

The node was at /models/EdgeEnumeration/equations/0/rhs all along and complete:
aggregate, bool_and_or, distinct, the skolem key over sorted endpoints, filter,
expr, ranges, output_idx. Only "id" was missing -- the one field the schema does
not require, which is why the fixture was schema-valid and reference-broken at
once. Its value is not a guess: the schema states that from_faq names the
producer by its id, so the id must be "edge_set". Placement matches the
near-twin fixture cadence/pure_topology.esm, which carries the same index_sets
names, ranges keys, output_idx and key shape -- and does carry the id.

The fixture now resolves and still validates. The two bindings that pinned the
rejection are unpinned: Go's referenceCorpusRejections and TypeScript's
KNOWN_UNRESOLVED. Those pins exist to turn a repair into a visible failure, and
they did. Neither binding's remaining entries are touched.

Corpus defect 3 -- DIAGNOSED, deliberately not fixed. It is a RESOLVER defect,
in all five bindings, not a fixture defect. esm-spec 4.9.5 and CONFORMANCE_SPEC
5.5.6 both make a join `on` key column polymorphic over three binder classes --
a node-local loop symbol, a document-scoped index set, and a declared local
variable -- and require a binding that diagnoses such a name to do so against
the variable AND index-set registries. Every binding's factor_scope consults
only three node-local sources and neither registry, though build_reference_graph
holds both. src_bin/tgt_bin are declared variables of the model, shaped over the
join's range index sets, and the engines bind them: Python's value-invention
pass returns join_key_buffers keyed by exactly those two names, and the fixture
validates clean.

The current rule is also self-inconsistent on fixtures everyone accepts:
join_filter.esm joins on a document-scoped index set that is in no args, no
ranges key and no output_idx, and survives only because no binding validates the
RIGHT column at all.

Not fixed here because the repair is a five-binding change to the same
reference_resolution/reference_graph modules being rewritten for defect 2, and
landing two independent rewrites of one module in parallel is how this drift got
made.

One consequence recorded loudly for whoever lands defect 2:
wildfire_atmosphere_ocean.esm carries the IDENTICAL latent join-factor failure
in its OceanDynamics model, masked today only because AtmosphericDynamics is
walked first. Fixing defect 2 alone does not make that fixture resolve -- it
changes which error it raises. Defect 3 must land with or before defect 2.

Corpus now: 92 valid fixtures, 90 resolve, 2 raise (was 89/3).
